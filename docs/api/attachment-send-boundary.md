# 编辑器附件发送边界（第 2 轮准备，2026-10-31）

当前主界面的图片、文件和截图选择入口保留，但**尚未接入真实媒体上传与消息发送的完整链路，附件暂不可发送**。本次修复只阻断错误出站，不将媒体功能记为完成，也不修改第 1 轮实机证据。

## 问题与当前行为

旧 `vbk/ui/apps/main/main.ts::handleSend` 会把所选附件转换为 `[附件] 文件名`，拼入文本后调用文本发送；附件自身没有上传，文件名文本不等于附件消息。真正的上游媒体上传/序列化证据见 [transports.md](transports.md) 和 `docs/api/evidence/2026-10-30/33-controlled-file-full-contract.json`、`44-image-body-and-auth-confirmed.json`、`68-controlled-video-upload.json`。适配函数存在不能证明编辑器已整体接入。

现在有附件时：

- 点击发送或按发送键会明确提示“附件发送尚未实现，草稿和附件已保留。请移除附件后再发送文字。”
- 草稿内容（包括空白）、引用和所选附件均保留，不创建发送中气泡，不调用翻译发送、文本出站 IPC 或 SDK，不清空草稿/附件。
- 附件栏持续显示文件名及“附件发送尚未实现”，移除按钮保留；选择按钮仍可见。
- 翻译栏的“发送原文”“发送译文”直接进入 `sendText`，直接翻译发送/重试进入 `translateAndSend`，这些旁路同样先检查附件并阻断，不能绕过主发送键的限制。
- 用户显式移除附件后，已有纯文本发送流程才可继续。不会自动只发文字、自动重试或偷偷发送文件名。

“零出站”指该次被阻断的发送尝试，不意味着整个应用没有后台轮询、已安排的翻译预览或此前选择/截图所用的本地媒体 IPC。选择文件/截图并不在本修复中伪装成上传完成。

## 实际调用边界与回归

`vbk/ui/apps/main/sendComposer.ts::sendComposer` 是 `main.ts::handleSend` 实际调用的编辑器出站边界：先检查附件，返回 `blocked_attachment`，再处理空文本或调用传入的文本/直接翻译发送回调。`attachmentSendUnavailable` 为旁路发送入口共享的能力检查；它不尝试上传、不生成媒体 URL，也不改变状态。

## 后续完成条件

真正开放媒体发送前，必须接通本地资产→按类型上传→有效上游资源→媒体消息正确编码→同 localid 回执/权威读回，并处理授权过期、上传成功但发送 unknown、撤回、大小/MIME 校验及失败后保留草稿。图片、文件、视频上传契约不同，截图最终也必须走真实图片链路，不能再以文件名文本兜底。

本修复仍需进入后续构建包做原生操作验收；当前只证明离线出站边界安全，未证明真实媒体功能完成。
