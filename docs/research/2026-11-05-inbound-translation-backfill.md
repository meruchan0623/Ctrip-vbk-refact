# 首条消息与历史入站翻译补拉

2026-11-05。本次修改尚未安装到正在运行的桌面客户端。修复基于本机宿主日志、既有官方实现取证，以及代码与浏览器回归；没有取得用户截图对应消息的原始响应，不能把该条消息的具体失败原因当作已经实证。

## 已核实的问题

- 宿主 `vbk.log` 在 14:20–14:22（UTC+8）有真实 `im_translate_messages` 请求结果，包含 `echoes=1`（原文原样返回）、`card=1`（适配器把行当作卡片后舍弃）。因此不能笼统说客户端从未请求，也不能把所有缺译文归因于携程没返回。
- 显示路径把消息类型 2/7 中的正文呈现为文本，翻译路径却只把 0 当作文本，导致类型 2/7 的返回正文被舍弃。现在共用 `uiKindOf` 与 `messageText`，也兼容数字字符串类型。
- [官方实现记录](2026-11-04-platform-message-translation.md) 的批量查译文请求使用空 `sessionId`、groupId 和 messageIdList。本项目却要求接待 session 非空且把当前 session 带入请求。现在按官方请求形态查询，不再让首条消息等待接待 session；跨接待 session 的历史消息也按原消息 ID 查找。账号代次和请求前后会话身份检查仍保留。
- 原来的快速重试结束后没有自动唤醒，历史外文 `unsupported` 还可能被永久缓存。现在未完成项保留低频补拉任务，未知选项不算明确关闭，明确关闭的选项缓存 60 秒后重新读取。

## 补拉行为

范围为当前打开会话中已经加载的文本和系统通知；滚动加载更早历史时，新增缺译文行自动加入。离开会话/账号失效/隐藏翻译时停止当前任务，返回时重新检查缺译文行，不跨账号写入，也不主动全量遍历所有会话历史。

每批最多 20 条、最多 2 批并发、最新消息优先。短期按 1/3/8 秒重试，最近消息继续使用已有较长预算；预算耗尽仍显示可重试状态，并按 30/60/120/300 秒退避，之后每 300 秒补拉一次，直到成功或离开作用范围。新消息与窗口焦点不能绕过这个冷却时间。

外文原样返回、`not_needed`、`unsupported`、空结果和网络错误不能把缺译文行永久标为完成。短外文与语言启发式未覆盖的文字也可补拉。中文或纯数字在明确不需要翻译的回答后停止。手动请求保留有界等待预算，失败后交由后台继续补拉。

修复了另一个历史队列边界：排队行在发出请求前离开列表，稍后重新加载时必须重新入队。已有译文异步进入列表时也会结束对应的手动等待。

运行日志新增 `translation.request/response/failed`，记录请求条数、历史条数、实际应用条数、原文回显和各类空结果计数，不记录正文、账号凭据或消息 ID。
