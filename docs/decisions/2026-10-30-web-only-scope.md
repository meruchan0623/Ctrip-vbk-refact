# 开发范围调整：以网页版为准

2026-10-30，Asia/Singapore。状态：用户已明确决定，覆盖此前按桌面客户端功能对齐的方案。

## 当前决定

> **2026-10-30 范围修订**：删减只针对左侧栏中携程自身的业务模块。本项目自行实现的客户端能力，以及后端/运行必需的能力全部保留。此前把多账号、托盘、商家助手、截图、更新等一并取消的表述作废。

1. 业务功能以当前网页版为基准：消息、通知，以及“按订单号找到客户并打开会话”。
2. **删除的只有携程自身业务模块**：首页、工作台、事件、公告、商服、产品、数据（BI）、点评、完整订单管理。不重建这些页面及其菜单墙、角标、内嵌业务页和桥接能力。
3. 订单只保留服务聊天需要的最小入口：输入完整订单号、查询、核对、打开详情、“IM 联系”进入正确会话。不承接确认、退款、核销、导出等订单操作。
4. **保留本项目自有功能**：多账号（每账号隔离）、系统托盘与任务栏未读、独立回复超时强提醒窗口、商家助手（TSim 登录、出站翻译、套餐速览、订单查询面板）、截图/OCR/中文纠错、客户端更新、本地诊断与偏好。这些不以“网页版是否有”为前提，按各自设计实现。
5. **保留后端/运行必需能力**：登录鉴权、身份隔离、消息传输与补偿、发送状态与恢复、本地存储、网络与凭据管理。
6. 携程业务接口仍以网页实际入口和证据为准：桌面包里的接口名、未启用分支、默认设置字段不能单独证明业务可用；写操作仍需样本验收。

## 订单与网页版本

本轮同时遇到新版 `vbooking.ctrip.com/vbk/im/main` 与订单实际跳转到的 `imvendor.ctrip.com/main`。两者都属于网页，但构建、UI、部分参数和轮询实现不同，不能把它们当作同一个部署。

已走通两条路径，详见[订单会话调查](../research/2026-10-30-web-order-conversation.md)：

- 订单列表 → 完整订单号查询 → 详情 → “IM 联系” → `14361/createimchat` → 返回的 IM URL → 客户会话。
- 新版消息页 → 输入订单号 → 查询结果 → 会话历史 → “开始聊天” → 当前会话输入框。

新实现优先使用目标网页已验证的链路。不得仅凭订单号自行拼接客户 UID、群号、业务线或供应商身份；不得把订单查询当作已取得联系客户的权限。

## 强提醒结论

用户手动切为在线后，本轮继续观察了 45 秒自然流量，未出现回复超时强提醒弹窗；此观察没有控制未回复消息的角色、时长和条件，不能单独证明该功能不存在。

进一步读取当前新版网页代码确认：它仍保留 `checkConvTimeout` 计算与 `reply_timeout` 事件，但网页适配器的 `sendCommonEvent` 只处理 `openExtraWindow`，没有处理 `reply_timeout`。当前网页的普通提醒由消息事件、本地声音、标题闪烁和浏览器通知完成，没有发现单独的强提醒业务接口。完整事实与边界见[提醒调查](../research/2026-10-30-web-reminders.md)。

用户随后明确要求保留独立强提醒窗口，覆盖此前取消该窗口的决定。因此把它作为本项目本地扩展：网页事实 → Rust 等待轮次/期限 → 单一 alarm 窗口。默认阈值 30 秒，确认有效商家回复或会话责任结束才清除；已读、打开会话、点击发送均不清除。采用 L0–L4 分级升级（L4 持续提醒默认关闭）并提供 5/10/30 分钟稍后提醒。方案与验收详见[独立窗口设计](../dev/03-strong-alert.md)，当前尚未实现或验收。

## 后续验收原则

- 每项能力需注明具体网页版本、真实入口、方法、请求字段、返回业务结果和 UI 读回。
- 静态代码只能把“未知接口”改为“已定位、未动态验证”，不能据此宣称可用。
- 发送、结束、转接、星标、评价等写操作的失败、权限与重复提交行为仍需对应样本；不因本次探查已打开会话就视为全部通过。
- 不为已删除的携程业务模块继续补接口或造本地替代页面；本项目自有功能按各自设计推进。
