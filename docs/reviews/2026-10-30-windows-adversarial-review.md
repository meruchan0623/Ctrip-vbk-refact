## 2. 必须先修订的 8 项设计问题

### R1 · P1 · 所有异步操作必须绑定账号、会话和视图代次

**位置：** [10 IM](../dev/10-im.md) 第 146–153、163–167 行；[09 助手](../dev/09-assistant.md) 第 235 行；[07 媒体](../dev/07-media.md) 第 269 行；对照 [04 业务页](../dev/04-business-pages.md) 第 244 行。

打开会话带 `buid`，但发送、草稿、历史、已读、关闭等多数命令只有 `gid/local_id`。助手槽位已有当前会话、草稿版本及切账号取消请求的措施，但 `sendText(text)` 仍未规定固定绑定哪个账号/会话；不能把这些已有保护视为全部缺失。下载还明确使用“当前账号 Cookie”，与来源 WebView 自带账号的方案冲突。

**反例：** A 的草稿防抖、翻译结果或下载尚未完成，main 已切到 B；A 的工作台仍存在，或两账号可访问同一 gid。此时按全局当前账号处理会错投操作。每账号独立 Profile/数据库不能自动解决异步请求归属。

**修订：** 公共契约定义 `AccountContext{env,buid,auth_generation}`、`ConversationRef{account,gid}`、`view_generation`；来源 WebView 的账号绑定由核心登记并校验。发送/译文替换另带草稿版本。下载在创建时捕获来源 Profile，续传、缓存和完成通知保持同一归属，不能中途读取全局当前账号。统一 04/07 的下载执行者与状态机。

**验收：** Mock 两账号共享 gid、同一下载 URL 返回不同账号内容，交错切号、草稿、译文、已读、下载和关闭回调；跨账号操作和陈旧结果覆盖均为 0。

### R2 · P1 · 登出必须阻断旧请求复活凭据

**位置：** [02 登录](../dev/02-account-login.md) 第 230、298 行；[06 网络](../dev/06-net.md) 第 97、201 行。

登出只列关闭窗口、断 IM、清 Cookie 和系统凭据；没有注销 net Jar 或隔离在途请求。`AuthExpired` / `CookieRenewed` 和鉴权失败接口只带账号。

**反例：** A 发请求后登出/重登，旧请求迟到的 Set-Cookie 将已删除 ticket 写回；或旧鉴权失败把新会话标为过期。actor 串行处理也不会自动识别旧消息。09 的 TSim `auth_generation` 不能代替携程账号的生命周期契约。

**修订：** 登出先禁发并递增账号认证代次，摘除 Jar，再关闭资源和清凭据；HTTP、IM、下载、校验结果携带并验证原代次。取消请求之外仍需拒绝无法取消的迟到结果。

**验收：** 挂起请求 → 登出/重登 → 释放旧续期/鉴权失败/完成事件；不得恢复旧凭据、作废新会话或错投结果。

### R3 · P1 · 发送协议缺少“不确定结果”，不能承诺无重复无丢失

**位置：** [10 IM](../dev/10-im.md) 第 135、177、246、268 行。

发送状态只有 `sending/sent/failed`；ack 才回填服务端 ID；socket 失败自动 HTTP 兜底，同时验收要求发送中杀 sidecar 后无重复无丢失。

**反例：** 服务端已经接受消息，sidecar 在返回 ack 前死亡。超时不代表未送达；自动 HTTP 兜底/重发可能重复。自发回推早于 ack 时，还会产生 msgId 行与 localId 行归并问题。

**修订：** 设计持久化 outbox、`unknown` 状态、稳定客户端请求标识、ack/回推归并。先核实服务端是否支持同一标识的幂等提交；未证实前不能以超时自动补发，也不能宣称端到端 exactly-once。

**验收：** 在提交前、服务端已收、回推前、ack 前分别终止测试 sidecar，并交换 ack/回推顺序；支持幂等时最终交付一次，不支持时进入可核对的 unknown，不误报成功、不自动重复发送。全部使用测试账号/模拟传输。

### R4 · P1 · “本地最新时间”不能充当完整同步水位

**位置：** [10 IM](../dev/10-im.md) 第 178 行。

当前补拉只比较会话最新时间，且从本地最新消息向后取。

**反例：** 断线漏掉 M2，重连先推来 M3；本地最新时间已与服务端相等，M2 永远不会补齐。同时间戳消息、多页离线消息也缺少明确终止规则。唯一索引解决去重，不能证明完整性。

**修订：** 分开保存“最新已见”与“已完整同步到”的水位。定义服务端分页/稳定排序、重叠读取、去重和推进水位的条件；一轮补拉完成前不能推进完整性水位。

**验收：** 乱序、同时间戳、先收最新后补历史、离线消息超过一页、翻页中重启；最终本地消息集合等于模拟服务端集合，重复为 0。

### R5 · P1 · 备份和恢复必须校验账号身份

**位置：** [05 存储](../dev/05-store.md) 第 141、165、169、286、292 行。

所有账号库都叫 `im.db`，统一目录中的备份却命名为 `<库名>-<日期>.db`，没有规定库名必须包含账号。库内主要表又去掉了 buid。

**反例：** 按文件名实现时，同日 A/B 备份碰撞；A 损坏后取到 B 的备份，表内也无法直接辨认归属。这里是路径约定缺口，不是本轮观察到实际覆盖。

**修订：** 数据、备份、隔离目录统一按 `(env,account,database)` 命名空间组织；库内保留不可混淆的身份/schema 元数据，恢复前强制核对。每日、升级前、迁移后备份另有唯一 generation，保留策略按账号独立执行。FAT/UAT/PROD 的凭据、Profile、数据库及备份须采用同一环境边界。

**验收：** 两账号同日多次备份、分别恢复；故意换错备份必须拒绝，不能显示另一个账号的记录。

### R6 · P1 · 旧数据导入重试不能清空正在使用的正式库

**位置：** [05 存储](../dev/05-store.md) 第 275、281 行。

导入在主外壳可交互后后台运行，失败重跑却要求先清空对应账号目标数据。

**反例：** 新 IM 已收到消息或用户修改状态，导入稍后失败重跑，清库会一起删除新版产生的数据。“可重跑”并不等于幂等。

**修订：** 在独立 staging 中导入、验证，再按明确的发布/合并协议接入正式库；或显式定义首次迁移期间的写入屏障。重试只能清理本导入批次，不能清整个账号库。

**验收：** 导入过程中持续写新消息及已读、星标等用户状态，在各阶段失败重跑；新版独有数据始终保留，旧导入批次不重复。

### R7 · P1 · Windows OCR 选型与 NSIS 安装身份未闭环

**位置：** [07 媒体](../dev/07-media.md) 第 12 行；[08 更新](../dev/08-update-telemetry.md) 第 125 行。

计划选择 `Windows.Media.Ocr`，却只定义普通每用户 NSIS 安装。Microsoft 明确该 API 对桌面应用的受支持使用要求 package identity；现计划没有身份包注册、更新、卸载路径。语言包缺失降级不能解决安装身份前提。[Microsoft OCR 文档](https://learn.microsoft.com/en-us/uwp/api/windows.media.ocr?view=winrt-26100)

**修订：** 决定采用具包身份的部署方式及其生命周期，或改用支持无包身份桌面进程的 OCR 引擎。不要先删掉全部现有 OCR 备选，再把普通 NSIS 调通作为假定。这里是受支持部署前提，不断言所有机器上的直接调用都会立即失败。

**验收：** 用正式签名安装产物，在最低支持 Windows 和干净普通用户环境测试 OCR；覆盖语言包有/无、离线、升级、卸载重装，记录实际 package identity。

### R8 · P1 · 旧安装包的有效签名不能授权本次降级

**位置：** [08 更新](../dev/08-update-telemetry.md) 第 95、103 行。

`release.json` 未签名，却能通过 `allow_downgrade_to` 授权回退，只要求目标旧包有签名。

**反例：** 策略清单/CDN 被替换，攻击者指向历史有效签名的旧版本。安装包签名只证明该包曾被签署，不能证明这次降级被授权。Tauri updater 的安装包 `.sig` 不自动覆盖本项目自定义的策略 JSON。[Tauri updater 文档](https://tauri.app/plugin/updater/)

**修订：** 对策略和回滚授权签名，绑定产品/渠道、目标版本、包哈希、序号与有效期，持久化防重放状态；定义最低安全版本、密钥轮换和正常升级/紧急回滚的不同校验条件。

**验收：** “历史有效签名包 + 伪造回滚字段”、跨渠道清单、旧授权重放都必须拒绝；只有匹配当前策略的受信回滚可执行。

### 性能验收口径需要固定

总纲“空闲内存 ≤ 官方 50%”可保留为待验证目标，不能写成架构本身保证。WebView2 仍使用多进程模型，同一环境中新域名仍可能产生 renderer；每个独立用户数据目录又有自己的进程组。[Microsoft WebView2 进程模型](https://learn.microsoft.com/en-us/microsoft-edge/webview2/concepts/process-model)

应分组测：同一机器、相同账号数/会话数据/页面/插件功能、相同预热程度，分别建立纯官方、官方+助手、新客户端的对照；记录 WebView2 Runtime 版本。纯官方组应在隔离测试环境建立，本轮没有卸载或禁用当前助手。

至少报告进程角色、Private Bytes、工作集（明确共享页口径）、CPU、句柄、进程增减，及输入/消息延迟 P50/P95/P99；前台、隐藏、双账号切换与 30–60 分钟驻留分别采样。2 秒启动预算只到本地壳时，另列“账号验证完成”“业务页可操作”“IM 已连通”的时间，避免壳快但业务迟到。
