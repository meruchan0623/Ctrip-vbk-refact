# 对抗性审查结论

**结论：当前不建议按这份计划直接开工。** 方向大体可行，但批次门槛存在循环依赖，多个工作项违反单写者规则，部分关键数字和验收定义不足以复现。另外，计划提出的后台保活方案尚未解决同账号互踢与隐藏 WebView 节流这两个路线级风险。建议先修订计划和工作项拆分，再启动 B0。

本次审查只读，未修改文件，也未运行测试。

## P0：会阻断执行或导致关键路径返工

### 1. B0 的退出条件要求完成一个排在 B1 的重构

B0 把 I-04 列为"前半"，但退出条件已经要求 `persist_rounds` 不再在主线程与全局锁内。I-04 又写明锁拆分是"后半段，在 B1 内完成"。这使批次边界不清：
- 如果 B0 只做前半，B0 的退出条件可能达不到。
- 如果把所有重构都放进 B0，B1 的"后半段"就失去定义。

计划位置：计划第 129 行（§3）和第 343 行（§5）。

代码确实在 `pump_rounds` 中调用 `persist_rounds`，后者执行 store commit：`vbk/src-tauri/src/state.rs:285`。计划对性能瓶颈的方向有依据，但 B0 退出条件把实现承诺提前了。

**建议：** 把 I-04 拆成两个可验收项。B0 只完成可独立验证的"持久化出主线程／合并写"。B1 再完成锁拆分和发事件时的锁边界。B0 退出条件只要求前半，不得引用未完成的 B1 后半。

### 2. I-05 把"互踢"既当风险又要求通过，验收语义互相冲突

计划说明隐藏页与浏览器网页 resource 相同，服务端会踢掉其中一个。同时它要求同账号并开浏览器 1 小时，被踢后 1 分钟内提示且不进入重连风暴，并把这条纳入 B1 退出条件（计划第 147 行 I-05，第 346 行 B1）。

这只能验证"被踢后能识别并停止重连"，不能证明客服可用。X11 还把"是否支持并用"留到 B1 开始前拍板（第 365 行）。

**建议：** 先把 X11 定为路线决策门。
- 若并用是支持场景，必须先证明 resource 冲突可解决或取得服务端确认，否则暂停隐藏 WebView 路线。
- 若不是支持场景，删除这条场景作为 B1 通过条件，并明确产品限制和提示文案。
- 把"无重连风暴"与"业务连续可用"分成两个验收结论。

### 3. B1 退出条件要求 I-05 节流原型"达标"，但没有可判定的阈值

I-05 要测 ping 周期漂移和"三次无应答"误判率，却没给允许漂移、误判率、样本数或设备矩阵。B1 退出条件直接要求"节流原型达标"（第 144 行、第 346 行）。同一工作项还把"最小闭环"与完整四级状态机并列，范围和完成标准不明确。

**建议：**
- 先定义原型测试矩阵、样本量和阈值。
- 把"路线可行性原型"和"完整监督器"拆成独立关口。
- 原型不通过时，写明停止或转路线的条件，而不是只写"X3 提前"。

### 4. 单写者规则被多处文件归属直接违反

计划规定同一批次每个文件只属于一个工作项 owner，但以下工作项的改动位置重叠：
- **I-04 与 I-05：** 都写 `adapter.rs`、`login.rs`。I-04 涉及同步命令、持锁事件，I-05 涉及 supervisor 和 WebView 重建（计划第 129 行起）。
- **I-08 与 I-28：** 明确要求同做，都涉及主窗消息列表与历史定位。I-28 的验收依赖 I-08，B1 又把它们放在同一通道，却没有指定文件级共同 owner 或提交顺序（第 167 行、第 287 行）。
- **I-02 与 I-29：** I-02 要改 `companion-card.ts` 并增加 CJK 门禁，I-29 又负责 i18n、发布包卫生和 CJK 门禁，两者还共同触及 UI bundle（第 110 行、第 294 行）。
- **I-14 与 I-17：** I-14 负责媒体发送，I-17 负责截图并要求插入草稿后发送，发送链路交叉所有权（第 212 行、第 231 行）。

这些重叠在源码里是实打实的。消息锚点逻辑在 `main.ts` 中直接读写 DOM dataset 和滚动位置（`vbk/ui/apps/main/main.ts:1557`）。消息树由 `messagePane` 创建并缓存（`main.ts:1897`）。两项并行修改容易互相覆盖。

**建议：** 启动前增加文件级 owner 表，逐文件唯一归属。需要协作时指定一个集成 owner，并写明先后顺序与接口冻结点。把 I-08 和 I-28 合并为一个工作流，或由同一 owner 先完成虚拟化接口、再接入锚点。

## P1：验收无法复现，或指标不能支撑计划结论

### 5. 多个关键数字缺乏定义或来源，部分指标互相不兼容

- **I-05 的 72 小时双账号测试（第 151 行）：** 每两分钟一条且"≥ 2000 条"。72 小时每账号约 2160 条，双账号合计约 4320 条。计划没说明"2000 条"是每账号还是总量，也没说明是否计入重连补偿，以及何谓丢失或迟到。
- **I-05 的延迟指标：** "p95 不高于官方同期 p95 + 1 秒"没有定义官方基线怎么采集。"p99 ≤ 10 秒"与前者的优先级也没写。
- **I-06 的频率指标（第 158 行）：** "适配器频率与官方页差异 ≤ 5%"没有定义分母、窗口，也没说失败重试是否计数。若官方 loop 活跃时适配器应只消费官方响应，适配器自身请求数应为零，此时拿它与官方请求频率做差异比较没有明确意义。
- **其他指标：** `1 Hz 调度抖动 p99 ≤ 50 ms`、`单写 p99 ≤ 20 ms`、`断电模拟 1000 次零损坏`、`桌面帧 ≤ 16 ms`、`体积预算` 都没说明硬件、数据量、统计方法、冷暖启动、故障模型或基线来源（I-04 第 135 行，I-25 第 281 行，I-28 第 287 行）。

**建议：** 每个数字补上测量对象、环境、采样窗口、分位数计算方式和证据路径。"零损坏"要描述注入的故障模型和恢复判据。性能阈值先设基线和目标，不要把未经定义的数字直接当批次门槛。

### 6. 一些门禁设计会误报，或检查对象与安全目标不匹配

- I-02 要用 grep/正则要求 `isTrusted`、`navigator.webdriver`、`innerHTML`、`new Function` 等零命中，范围包括源码与工具。计划只对 DOM sink 排除 `*.test.ts`，没有明确排除门禁自身、文档、合法注释或受控兼容代码。源码测试本身确实用到 `new Function`，例如 `vbk/ui/apps/main/conversation-business.test.ts:27`。检查边界不明确，门禁可能因测试实现或合法字符串而失败，而不是因生产代码风险失败。
- `commands.ts` 与 `commands.txt` 的"黑名单词根零命中"容易把合法窄命令误判为危险命令。反过来，命令名不含危险词也不代表其参数和授权范围安全（第 113 行）。

**建议：**
- 对生产代码目录做语法级检查，或限定扫描文件清单。
- 对允许的测试辅助 API 建显式例外。
- 把安全检查从词根黑名单改成能力清单与授权矩阵验证。
- `strings | grep` 不适合作为 DevTools 是否可用的决定性证明，应验证 release feature 配置和实际运行行为。

### 7. B2/B3 顺序与条目依赖不一致

- I-18 写明 Intel 包应提前，B2 退出条件要求签名安装包"含 Intel 包"。但 I-27 又把 universal 或分别出 arm64/x86_64 包列在 B4（第 237 行、第 347 行）。若 B2 的 Intel 包依赖 I-27，批次顺序就倒置了。若不依赖，应明确 I-18 的构建产物如何生成、由谁维护。
- I-02 要检查 `lipo -archs` 与签名 entitlements，但 B0 先于 I-18 的签名工作。对尚未产生的 release 产物，门禁是条件跳过、只在 release workflow 执行，还是阻塞 B0，计划没有定义（第 117 行）。

**建议：** 明确开发 CI 与 release CI 的不同触发条件。若 Intel 包是 B2 必需项，把构建支持从 I-27 移到 I-18，或单列为前置任务，并在依赖图上标注它先于 B2 验收。

### 8. "目标机证据"要求与批次定义不一致

文档开头（第 14 行）声明模块完成必须有目标机读回证据。但 I-04 的验收是本地基准，I-02 是 CI 反例测试，I-03 是集成测试。第 5 节（第 350 行）又要求每批交付"目标机版本号与 hash、受控样本、读回结果"。"目标机"到底指安装包用户环境、官方网页还是开发机并不清楚，导致纯代码门禁无法满足该批交付格式。

**建议：** 把"代码门禁证据"和"业务目标机读回证据"分开定义。为每个工作项标注适用的证据类型，不要求所有条目都提供不适用的实机读回。

## P1：漏掉的安全和稳定性风险

### 9. I-05 的后台保活开关可能扩大 WebView 攻击面，且没有兼容性验证

I-05 建议给 WebView2 传入关闭后台节流和 renderer backgrounding 的启动参数（第 148 行）。计划没说明：
- 这些参数是否受 Tauri/WebView2 当前 API 支持；
- 它们是否仅作用于官方页 WebView，是否影响资源消耗和其他 WebView；
- 有无安全评审或退出策略。

**建议：** 把参数路线列为实验分支，记录目标 WebView、实际生效证据、CPU/内存上限和失败回退。不要先写成默认做法。需要对照"不传参数"的行为，并把它列为风险决策，而不是默认保活方案。

### 10. 持久化改造的并发、崩溃恢复和数据新旧次序未进入 I-04 验收

计划把持久化改为脏标记、调度器合并写和专用线程。但它没说明：
- 数据快照如何在锁外安全生成；
- 同一 namespace 多次提交如何排序；
- 退出或崩溃时如何 flush；
- 写失败怎样反馈。

代码当前持有 `Mutex<Cores>` 的路径会调用 `persist_rounds`（`vbk/src-tauri/src/state.rs:285`）。I/O 移出锁后，这些问题会成为正确性条件，而不只是性能优化。

**建议：** 在 I-04 明确快照版本/序号、单写者队列、失败重试与关机 flush 语义。用并发写入、提交乱序、磁盘满和进程强杀测试，验证无旧快照覆盖新状态。

### 11. 更新器"安装前平台签名校验"缺少失败边界和发布信任链描述

I-19 正确指出 updater 只验 minisign，并提出自行校验平台签名（第 243 行）。但计划没有定义：
- 签名验证发生在解包前还是安装执行前；
- 验证失败是否保证完全不启动安装器；
- minisign 公钥轮换和私钥泄漏后的恢复策略。

**建议：** 补上信任链与密钥轮换/撤销方案，并明确验证失败必须阻止任何安装脚本执行。在 Windows 和 macOS 分别验证更新包从下载到安装器启动的完整路径。

## P2：范围或估算可精简

### 12. I-02 把多类发布治理任务塞进一个门禁工作项

I-02 同时要求安全 lint、契约一致性、宿主双平台测试、包体积比较、架构断言、签名断言、mock 清理和口令 schema 检查（第 110 行）。这横跨 B0、B2 和 release 产物阶段，部分还依赖 I-18/I-29。

**建议：** I-02 只保留 B0 可执行的源码门禁与反例测试。把包体积、签名、架构和 mock 出包检查移到各自产物工作项，避免一个门禁项长期处于"部分完成"。

### 13. 部分指标可能优化过度，建议先用实测决定是否保留

这些指标都应先定义产品目标与场景：
- "体积与上一次比较"；
- `1 万条消息单帧 ≤16 ms`；
- 固定 30/30 阅读位置通过；
- "连续 5 次升级钥匙串不弹授权"。

计划本身记录的 73 ms 是源码微基准／审查发现，还需要真实运行环境验证，不应直接把未经实机确认的数字转成发布门槛（I-08 第 167 行，I-18 第 240 行，I-28 第 287 行）。

**建议：** 先保留观察指标和性能基线，再把有用户影响且可稳定复现的目标升级为硬门槛。不要为达到未经确认的阈值做大规模虚拟化或发布流程改造。
